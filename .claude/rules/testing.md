# Testing

General testing guidance for any project in this workspace. When a project ships its own
test suite, run it from the correct environment before pushing. CI is `privacy-scan.yml`
(free, static) plus `review.yml` (billed, Claude-driven; see "CI" at the end of this file for
both), so the test SUITES themselves are still run manually.

## Principle

- Test the behavior that matters: a script's contract (inputs, outputs, error paths), not
  its internals.
- Prefer fast, deterministic tests. Patch slow or network-bound dependencies (model loads,
  remote APIs) with fixtures so the suite runs offline where possible.
- Use tolerance-based comparison for floats (e.g. `assertAlmostEqual`, `places=2`).
- Document an expected timeout in a comment for any long-running test.

**R20 - every suite asserts at least one failure path, not only the happy path.**
A test that can only pass proves nothing about the code and everything about the
test. The defects that mattered here were all caught by a negative case: a swept
rung clamped above the native window, a tag that spills out of VRAM, a truncated
JSON header, and a `create` on an existing file writing a numbered duplicate. A
check with no demonstrated failure is a check nobody has run.

**R34 - a fixture never carries a real identity.**
Test data, examples in a `SKILL.md` and plan snippets use fictitious names, emails and
identifiers (`Wick, J.`, `student@example.org`, `XXXX000000`, `XXXYY1234`), never a real
student, co-author, account name or machine path, even one that is public elsewhere. The
privacy guard (`.claude/hooks/git/`) catches the SHAPES - account paths, code permanent,
`@etu.uqac.ca`, FRQ id - but no pattern can recognise a real name, so this rule is the only
protection for names. Measured 2026-10-01: the public repository carried real student names
in fixtures, and purging them took a full history rewrite.

**R21 - no test reads machine-local measured configuration.**
`.claude/local-model-config.json` is gitignored and describes one GPU, so a test
that reads it passes only on the machine that wrote it and fails everywhere else
for a reason that looks like a defect. Inject the number the test needs as a
fixture, so the same suite gives the same verdict on any clone.

## Environments

- Use the project's own virtual environment for the layer you are working in (a repo may
  have more than one `.venv`). Activate it before running scripts or tests.
- Never mix dependencies across environments.

## CI

Two workflows. `.github/workflows/privacy-scan.yml` scans the commits a push or a pull
request adds with betterleaks and `.claude/hooks/git/privacy-rules.toml` (secrets plus
personal-data shapes). It is the authoritative gate behind the local pre-commit hook, which
`--no-verify` can skip, and it is reusable by the lab's other public repositories, free
(static scan, no model call).

`.github/workflows/review.yml` (Issue #65) runs on every same-repo `pull_request` (opened,
synchronize, reopened; fork PRs are skipped because they get no secret; no
`workflow_dispatch`, since the diff step needs the pull-request event, so a forced re-review
is an empty commit). A headless `anthropics/claude-code-action` session reads a pre-computed
diff (capped by `MAX_DIFF_BYTES`, an unmeasured author's choice, cut on a line boundary, with
the files `install.ps1` regenerates left out) and drives `security-review` and `code-review`
(effort high), the two skills built into Claude Code. The model session posts nothing. A later
step with no key and no agent, `scripts/ci/review_mirror.py` (settings and their provenance in
`scripts/ci/review-mirror.json`), sanitises the reply and creates or updates ONE marked PR
comment. The workflow has two jobs with separate permissions: `review` (the API key,
`pull-requests: write`, no `issues: write`) and `mirror` (`issues: write`, no key, no agent),
so no job holds the key, the agent and Issue write access together. `mirror` copies that
comment, by id, onto the open Issue named by a line starting `Fixes #N` or `Closes #N`, as ONE
comment updated in place (it mentions the PR author only when it creates it, and assigns the
author, which is allowed to fail for a non-collaborator). Without the secret the first step
says so and the rest of the job is skipped, so the check ends neutral instead of red. Unlike
privacy-scan it is billed, and it needs a repo secret `ANTHROPIC_API_KEY` that only the
operator adds.

Design choices, each from a review finding on this change (PR #67). The action runs in agent
mode only: `track_progress` and `use_sticky_comment` are NOT set, because measured from the
action source at the pinned SHA (`src/modes/detector.ts`, `src/modes/tag/index.ts`)
`track_progress` forces its tag mode, which adds `Bash(git add|commit|rm)`, a push wrapper,
`acceptEdits` and CI-log tools to the session, and the earlier "no Bash" claim was false while
it was set. `--tools "Skill,Read,Grep,Glob"` makes those the only tools that exist, with no
`Bash`, `Edit`, `Write` or `Agent`, because the diff is untrusted and the key sits in that
process. `Read`, `Grep` and `Glob` of `/proc`, `/sys` and `/run` are all denied (nine rules),
since `/proc/self/environ` would otherwise hold the key. After the run,
`review_mirror.py check-tools` reads the session's own tool list from the execution file and
fails the job on a forbidden tool or on a list it cannot read: detection after the fact, while
prevention is the flag and the static suite. The checkout keeps no credential
(`persist-credentials: false`). The workflow loads NO plugin: `ai-firstify` and `tech-debt`
were removed from CI (2026-10-12) because the action installs a plugin only from a marketplace's
moving default branch (its URL check, in `base-action/src/install-plugins.ts`, accepts a bare
`.git` suffix and no ref or SHA), so third-party code that can change unreviewed would load in
the step holding the key. They stay available in local sessions. Restoring them in CI needs
ResearchTools' own reviewed skills (R36 part 3), not a vendored copy (R36 part 4).

Residual and declined, with the measurement. A collaborator with write access can push a
branch whose `review.yml` is modified, and a same-repo pull request runs that version with the
secret: the `Main protection` ruleset requires a code-owner review and the `privacy-scan`
check only for merges into `main` (read with `gh api` 2026-10-16), and `.github/CODEOWNERS`
is `* @LARi-UQAC`, so nothing gates the RUN. The first run therefore uses a throwaway key with a
low spend limit, and the key is rotated afterwards. "Fixes #N" lets a PR author pick any open
Issue to receive the copy: declined, since opening a PR already needs write access.

UNVERIFIED (R15), no test exists and none can run offline: that the deny-rule path syntax
blocks `/proc` reads; that the pinned Claude Code honours `--tools` and writes a `tools` list
in the `init` message of the execution file (the guard fails closed when it does not); that
`security-review` and `code-review` are invocable through the Skill tool in a headless run (the
prompt makes Claude state which skills ran, so a gap is visible); that `pull-requests: write`
alone lets the GITHUB_TOKEN create the PR comment. Only a real run on a throwaway PR proves
them. What is checked offline: the YAML parses, and `.claude/hooks/Test/test_review_workflow.py`
asserts the workflow's static properties and the script's logic against a fake `gh`.

Everything else is run manually before pushing.
