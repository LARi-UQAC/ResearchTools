    Profiles & Environment¶

    Chapter 02 of the ResearchTools manual. Back to table of contents.

    Profiles¶

    A domain profile centralizes everything domain-specific (Scopus subject areas and exclusions, topical-relevance signals, off-topic flag, stats profile, author, course context, language) in one YAML file under profiles/, so the agents and skills stay shared across users and labs: one maintained core, N profiles.

    Profile Domain Author Default
    engineering.yaml Mechanical / electrical / ML / control / systems engineering Martin Otis (UQAC) yes
    cosmetic.yaml Cosmetic / formulation science (SPF, microbiome, dermatology, sensory) Lionel Ripoll (UQAC) no
    _template.yaml Copy it to profiles/<domain>.yaml to add a new domain - -

    The active profile is recorded in .claude/CLAUDE.md as the machine-readable line active_profile: <name>. Select it at install time (.\install.ps1 -Profile <name>, or the interactive prompt) or edit that line directly. Currently wired consumer: scopus-researcher (search clauses, Step 3a relevance check, synthesis framework); the remaining fields (author, stats_profile, course_context, language) are schema-ready and will be wired incrementally. Field-by-field spec, fallback rules, and the add-a-profile procedure: profiles/README.md.

    Environment variables / API keys¶

    Set these at the Windows User scope (PowerShell), then restart Claude Code:

    [System.Environment]::SetEnvironmentVariable('SCOPUS_API_KEY', 'your-key', 'User')
    Variable / source Required for Where to get it
    SCOPUS_API_KEY Required — all /scopus, /auditreview, /auditpaper, /auditthesis, /litreview, /litupdate, /bibclean, /replyreviewer, and PDF retrieval Elsevier Developer Portal
    .scopus_key file Fallback for SCOPUS_API_KEY — place the key in .claude/skills/scopus/.scopus_key (gitignored) same key as above
    UNPAYWALL_EMAIL Optional — enables the Unpaywall open-access tier in download_pdf.py (HTML/PDF fallback when no publisher PDF); a plain contact email, or pass --email any institutional email
    GEMINI_API_KEY Optional — the Gemini leg of the deliberation panel (cross-review, table enrichment). The model is resolved at run time from Google's own catalogue (--gemini-model auto), so no model name is set here Google AI Studio
    COPILOT_TOKEN or GH_OAUTH_TOKEN Optional — the GitHub Copilot leg of the deliberation panel. GH_OAUTH_TOKEN is exchanged automatically for a Copilot token. Without either, the panel uses a local Ollama model declared for the session role as the second voice, and without that too the leg is skipped without stopping the pipeline your GitHub account with Copilot
    GITHUB_TOKEN Legacy — Copilot refuses a personal access token and GitHub Models was retired on 2026-07-30, so this variable no longer gives a cross-review leg. It is still the last attempt of the provider chain GitHub → Settings → Developer settings
    S2_API_KEY (or SEMANTIC_SCHOLAR_API_KEY) Optional — Semantic Scholar author/PDF backfill and keyword search; without it the throttled public pool is used, where a search can be refused (429) and exits 1 Semantic Scholar API key request
    --insttoken (CLI flag, not an env var) Optional — off-campus Elsevier access when not on the UQAC network/VPN UQAC library / Elsevier institutional token

    An on-campus network connection or active UQAC VPN is required for Scopus access unless an --insttoken is supplied. Secrets are kept out of git: .env, secrets/, and credentials/ are listed in .gitignore.

    Python environments: every library¶

    A skill that imports a library nobody declared works on the machine that happens to have it and fails on every other one, so this section lists every third-party library the repository's Python code needs, one row per library and per environment. The repository has three environments, all built in the main clone by .\setup.ps1 -InstallPython from one data file, scripts/lib/rt-python-requirements.json:

    • .venv-skills, for the skills, the hooks' tests and the offline suite;
    • .venv-docs, for this site;
    • .venv-pdf2md, for the pdf2md conversion.

    The three are independent, so a library used in two of them has a row in each table with its own pin.

    The tables below are generated, not written by hand. scripts/docs/python_libs.py reads the data file, every requirements file it names, and the import statements of every .py file under .claude/skills, .claude/hooks and scripts, then fills the tables between the python-libs marker comments of this page. How to read them:

    • ☑ in the first column means a requirements file declares the library. ☐ means the code imports it and no file declares it, which python_libs.py --check reports as an error.
    • "Pin" is the version the requirements files fix, not a version measured on a machine. python_libs.py --drift compares it with what an environment holds.
    • "Optional" means the import is guarded (inside try or a function) or the requirements line says so.
    • The notes, licences included, come from scripts/docs/python-libs-notes.json.
    • Programs that are not pip packages (pandoc, Poppler, MiKTeX, Ollama, Node.js) are in the Prerequisites table of chapter 01.

    .venv-docs¶

    The interpreter that builds this site (see chapter 16). It holds requirements-docs.txt, every line pinned, transitive dependencies included. The site needs mkdocs and mkdocs-material (the theme), pymdown-extensions and Markdown (the extensions listed in mkdocs.yml: attr_list, md_in_html, tables, toc, pymdownx.superfences, pymdownx.highlight and pymdownx.slugs), ghp-import (the gh-deploy command), Pygments and PyYAML. Those are direct in the Role column, and every other line is transitive. The build hook scripts/docs/mkdocs_hooks.py uses the standard library only. Eleven lines that nothing in this environment required were removed on 2026-10-22. A .venv-docs built before that date still holds them until it is deleted and rebuilt.

    .venv-pdf2md¶

    The interpreter of the pdf2md conversion (mineru, mineru-llama-cpp). It is kept apart from .venv-skills by the owner's decision of 2026-10-22: mineru 4.0.11 needs gradio, every gradio up to 6.30.0 caps pillow below 13.0.0, and 13.0.0 is the version that clears the advisories of pillow 12.3.0 in .venv-skills. This environment therefore keeps pillow 12, with its advisories accepted and recorded in IMPROVEMENTS.md.

    The form service¶

    deploy/form-service/ has its own environment, %LOCALAPPDATA%\ResearchTools\venv-form-service, which setup.ps1 does not build. It is described by deploy/form-service/requirements.txt: fastapi==0.141.1, uvicorn==0.54.0, pypdf==6.21.2, pyHanko==0.37.0, cryptography==50.0.2 and requests==2.34.2. Its pins of the libraries it shares with the form-service skill are the same, and verify-python-env.ps1 checks that. The service tests run in that environment, not in .venv-skills.

    Keeping these tables true¶

    A change that adds an import of a new third-party library also adds its line to the skill's requirements file, with an exact version checked by pip-audit (chapter 16). A new requirements file is also named in scripts/lib/rt-python-requirements.json. Then, with the .venv-skills interpreter:

    python scripts\docs\python_libs.py --write    # regenerate the tables of this page
python scripts\docs\python_libs.py --check    # exit 1 on an omission or a stale table
python scripts\docs\python_libs.py --drift    # compare the pins with what each environment holds

    scripts\test\verify-python-libs.ps1, run by run-all-checks.ps1, fails when --check does. An import the notes file cannot map to a distribution is reported too, and a new entry in scripts/docs/python-libs-notes.json fixes it.
